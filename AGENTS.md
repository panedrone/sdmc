# AGENTS.md

Notes for coding agents. Two cases: **using** sdmc in another project, and **working on** sdmc itself.

## Using sdmc in a project

Follow [plugins/sdmc/skills/sdmc/SKILL.md](plugins/sdmc/skills/sdmc/SKILL.md): init → `<db url>` →
`sdmc xml` → `sdm.xml` → `sdmc gen` → `sdmc val`. In short:

- Generate, do not hand-write: models and DAO come from `sdm.xml` plus the live database.
- Never edit generated files (`Code generated by a tool. DO NOT EDIT.`); change `sdm.xml`, regenerate.
- The data store adapter (`DS`, `DataStore`, `Set...`) is not to be changed; the `_ex` file is the project's.
- `sdmc val` exit 0 is the proof that the code matches the XML and the schema.

Claude Code: `/plugin install sdmc --marketplace panedrone/sdmc` installs that skill.

## Working on sdmc

Go module `github.com/panedrone/sdmc`, the binary is `cmd/sdmc`.

- `cmd/sdmc`: the CLI, commands, flags, `.sdm`
- `internal/sdmxml`: reads `sdm.xml`, external `<dao-class>` files and `settings.xml`
- `internal/meta/<db>`: metadata of PostgreSQL, MySQL, SQLite, SQL Server
- `internal/gen`: a generation run, `settings.xml` + `sdm.xml` to files
- `internal/cg`: the SQL of a method, its fields and parameters, shared by the generators
- `internal/gogen`, `internal/pygen`, `internal/cppgen`: Go, Python, C++ (ports of the plug-in's Java and VM templates)
- `internal/skeleton`: `sdmc init`, XSD, data store files
- `internal/assist`: `sdmc xml`
- `datastore/templates`: the source of every data store; `datastore/<db>/...` is generated from it
- `cli/`: design-time, not shipped: `dsgen` builds data stores from templates, `genharness` and
  `metadump` compare with the Java plug-in

Before a change is done, the same as CI (`.github/workflows/ci.yml`):

```bash
gofmt -l .                 # empty
go vet ./...
go test -race ./...
go run ./cli/dsgen && git diff --exit-code -- datastore
```

- Tests need no database server: they generate from SQLite databases they create; PostgreSQL,
  MySQL and SQL Server code is tested without a connection (SQL Server on a fake database/sql
  driver, `internal/meta/mssql/fake_test.go`). Do not add tests that need one.
- Edit data stores in `datastore/templates` only, then `go run ./cli/dsgen`; never the generated copies.
- The generated code must stay byte for byte what the IDE plug-ins
  ([sqldalmaker](https://github.com/panedrone/sqldalmaker)) generate for the same XML. Except C++:
  its type map knows the driver names only, a type without a key goes to the compiler as the driver
  names it.
- A behaviour change goes to `README.md` in the same commit; the skill and `llms.txt` too when the
  workflow, a command or an option changes.
- Releases: a tag `vX.Y.Z` runs `.github/workflows/release.yml` (goreleaser).
