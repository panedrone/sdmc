# go-sdm

[![CI](https://github.com/panedrone/go-sdm/actions/workflows/ci.yml/badge.svg)](https://github.com/panedrone/go-sdm/actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/panedrone/go-sdm.svg)](https://pkg.go.dev/github.com/panedrone/go-sdm)
[![Go Report Card](https://goreportcard.com/badge/github.com/panedrone/go-sdm)](https://goreportcard.com/report/github.com/panedrone/go-sdm)
[![License: ISC](https://img.shields.io/badge/license-ISC-blue.svg)](LICENSE)

SQL DAL Maker for Go generates the data access layer — models and DAO — from an XML manifest
and the metadata of a **live database**. One static binary, no runtime dependencies.
PostgreSQL, MySQL and SQLite. The same binary generates Python and C++ (Qt) too, without ORM
(see [Python](#python) and [C++](#c-qt)).

**SQL first, no ORM, no reflection at run time:** you write SQL or point at a table, the
database says what the columns and parameters are, and you get plain Go functions to call.

## A minute with it

A database with the tables `groups` and `tasks`, a Go module. Create the configuration, ask the
database for a starting manifest, generate:

```bash
sdm init -dir go-sdm -dao internal/dbal -orm no_orm -db sqlite   # set <db url> in go-sdm/settings.xml
sdm xml -orm no_orm                                              # paste it into go-sdm/sdm.xml
sdm gen
```

`sdm xml` reads the schema, foreign keys included:

```xml
<dto-class name="Group" ref="groups"/>
<dto-class name="Task" ref="tasks"/>

<dao-class name="TasksDao">
    <crud dto="Task" table="tasks"/>
    <query-dto-list dto="Task" method="getTasksByGroup(gID)" ref="tasks(g_id)"/>
</dao-class>
```

`sdm gen` writes `internal/dbal/models/task.go` and `internal/dbal/tasks_dao.go`, ready to call:

```go
type Task struct {
    TID       int64  `json:"t_id"`
    GID       int64  `json:"g_id"`
    TPriority int64  `json:"t_priority"`
    TSubject  string `json:"t_subject"`
    TComments string `json:"t_comments"`
}

var CreateTask = func(ctx context.Context, item *models.Task) error { ... }
var ReadTask = func(ctx context.Context, tID int64) (*models.Task, error) { ... }
var GetTasksByGroup = func(ctx context.Context, gID int64) (res []*models.Task, err error) { ... }
```

Add a method to the manifest with your own SQL, run `sdm gen` again; `sdm val` in CI fails when
somebody changed the schema or the XML and forgot to regenerate.

**Install:** a binary for Windows, Linux or macOS from
[Releases](https://github.com/panedrone/go-sdm/releases), or with Go:

```bash
go install github.com/panedrone/go-sdm/cmd/sdm@latest
```

Or open the repository in a [dev container](#try-it-in-a-dev-container) (VS Code, GitHub Codespaces):
Go, `sdm` and PostgreSQL with a demo schema are ready in it.

It works like the [SQL DAL Maker IDE plug-ins](https://sqldalmaker.sourceforge.net/):

- **XML manifest.** The manifest describes what to generate: the models, the DAO functions,
  and the SQL behind them.
- **Translate.** The manifest is translated into complete Go code, free of any direct call to
  database/sql, sqlx or gorm. Those stay behind a data store that you own (see
  [Data store](#data-store)).

```xml

<dto-class name="Test" ref="tests"/>

<dao-class name="TestsDao">
<crud dto="Test"/>
<query-dto-list dto="Test" method="GetTestsByRating(t_rating)" ref="tests_by_rating.sql"/>
<exec-dml method="SetTestRating(t_id, t_rating)" ref="call set_test_rating(?, ?)"/>
</dao-class>
```

**Reverse engineering** is at the heart of it. During translation the generator reads live
metadata — tables, views, the result sets of your own SQL, the parameters of procedures — to
resolve everything the manifest leaves open. That is why the database must be up and reachable
whenever you generate. Parsing the DDL would not do: the database knows what DDL doesn't show —
views, functions, procedures with `INOUT` parameters, ref-cursors, the real types of query
columns. The manifest persists, so regeneration is repeatable: when the schema changes, you
re-run the generator and your corrections are still there.

**DAO are package-level functions in variables**, no structs, no interfaces to implement:

```go
var GetTestRating = func (ctx context.Context, tID int32) (res float64, err error) { ... }
```

A test replaces the one it needs and puts it back, no mocking library, no database:

```go
saved := dbal.GetTestRating
dbal.GetTestRating = func(ctx context.Context, tID int32) (float64, error) { return 4.5, nil }
t.Cleanup(func () { dbal.GetTestRating = saved })
```

A working
example: [sdm_todolist_go_react_vue_npm_sqlite3](https://github.com/panedrone/sdm_todolist_go_react_vue_npm_sqlite3)
(Gin + SQLite, React and Vue front-ends), its data
layer [internal/dbal](https://github.com/panedrone/sdm_todolist_go_react_vue_npm_sqlite3/tree/master/internal/dbal)
is generated by go-sdm and covered by a DAO test on the live database.

## Quick start

Install `sdm` (see [above](#a-minute-with-it)), then in the folder of `go.mod`:

```bash
sdm init -dir go-sdm -dao internal/dbal -orm no_orm -db pg
```

All four options are required (see [Options of `init`](#options-of-init)): `init` writes files, and
a forgotten option must not put them somewhere else. Without one of them nothing is written, and
`sdm` prints the help of `init`, an example and the table of options; `sdm help init` prints it too.

`init` creates the configuration:

```
go-sdm/sdm.xml                         classes to generate
go-sdm/settings.xml                    folders, database URL, type map of the database
go-sdm/*.xsd                           completion and validation in the IDE
internal/dbal/data_store_no_orm.go     the data store used by the generated code, for the database
internal/dbal/data_store_no_orm_ex.go  your part: connection
```

and prints the line for `.sdm`, the root file of the IDE plug-ins: `go-sdm/go.dal` (see
[Several configurations](#several-configurations-sdm)).

The generated code goes under `internal/`: the DAO and the models are the data layer of your
application, not an API for other modules, and the Go compiler keeps them so. Deeper folders work
the same way, for example `internal/noorm/dbal` (`-dao internal/noorm/dbal` of `init` or
`scope` in `settings.xml`).

Describe classes in `go-sdm/sdm.xml`, set `<db url>` in `go-sdm/settings.xml` and run
`sdm gen`: it generates models and DAO. It also keeps the XSD in step with the version of `sdm`.
`sdm` without a command only prints the usage.

| command                   |                                                                                       |
|---------------------------|---------------------------------------------------------------------------------------|
| `sdm init`                | creates the files above; if any of them exists, it is an error and nothing is written |
| `sdm generate`, `sdm gen` | generates into the folders of `settings.xml`, writes only what changed                |
| `sdm validate`, `sdm val` | for CI: exit 1 if somebody changed the XML or the database and forgot to regenerate   |
| `sdm list`, `sdm ls`      | the classes of `sdm.xml`, numbered in the order of declaration                        |
| `sdm xml`                 | the starting XML from the database schema, to the console                             |
| `sdm datastore`, `sdm ds` | updates the data store of the DAO folder to this version of `sdm`                     |
| `sdm version`, `-v`       | the version (also `--version`)                                                        |

`ls` prints one line, `ls -l` a table with the generated files and their dates:

```
$ sdm ls
1:Task  2:TasksDao  3:Group  4:GroupsDao
$ sdm ls -l -d
#  kind  class      file                         modified
2  dao   TasksDao   internal/dbal/tasks_dao.go   2026-10-13 14:02:05
4  dao   GroupsDao  internal/dbal/groups_dao.go  -
```

`gen`, `val` and `ls` take classes by those numbers or by names, by spaces or commas; none
means all of them. `-m` keeps the models only, `-d` the DAO only:

```bash
sdm gen 1,3 GroupsDao
sdm val -d
```

`sdm xml` reads the tables and views of the database and prints what the XML assistants of
the IDE plug-ins make: `-m` a `<dto-class>` for each of them, `-d` a `<dao-class>` for each,
named by the table (`tasks` → `TasksDao`), with a `<crud>` and the access by foreign keys
inside. Classes already in `sdm.xml` (a `<dto-class>`, a `<crud dto>`, a `<dao-class>` of the
same name) are skipped, so after a new table `sdm xml` prints only it; if nothing is left, the
reason goes to stderr. `-force` prints all tables and views anyway, without reading `sdm.xml`.

`-orm no_orm|sqlx|gorm`, the same values as in `init`, is required, without a default: it is the
model of the DTO classes (see [database/sql, sqlx or gorm](#databasesql-sqlx-or-gorm)), `Task`,
`sqlx-Task` or `gorm-Task`, in `<dto-class>` and in the DAO classes. A class already in `sdm.xml`
is skipped whatever its model: `gorm-Task` is skipped if there is `Task`.

```
$ sdm xml -orm no_orm -m
<dto-class name="Group" ref="groups"/>
<dto-class name="Task" ref="tasks"/>
$ sdm xml -orm gorm -m
<dto-class name="gorm-Group" ref="groups"/>
<dto-class name="gorm-Task" ref="tasks"/>
$ sdm xml -orm no_orm -d
<dao-class name="GroupsDao">
    <crud dto="Group" table="groups"/>
</dao-class>
<dao-class name="TasksDao">
    <crud dto="Task" table="tasks"/>
    <query-dto-list dto="Task" method="getTasksByGroup(gID)" ref="tasks(g_id)"/>
</dao-class>
```

`<crud/>` without inner elements makes all five methods with default names; add `<create/>`,
`<read-all/>` and the others inside only where you need other names or fewer methods.

The output goes to the console only, so it chains like any other command:

```bash
sdm xml -orm sqlx -m > models.xml           # to a file
sdm xml -orm sqlx -m >> models.xml          # appended to a file
sdm xml -orm sqlx | clip                    # to the clipboard: clip on Windows, pbcopy on macOS
```

Paste it into `sdm.xml` as is: models and DAO classes are ready elements of `<sdm>`. Never
redirect into `sdm.xml` itself: the shell empties the file before `sdm` reads it.

PowerShell 7 writes UTF-8 with `>` as well. Windows PowerShell 5.1 writes UTF-16 with `>` by
default, which `sdm` does not read, so there use `Out-File`:

```powershell
sdm xml -orm sqlx -m | Out-File -Encoding utf8 models.xml
```

As in the plug-ins, the names of DTO classes are English singulars of the table names, and
all schemas but the system ones are read, without the schema in the XML.

### Options of `init`

All of them are required, `init` has no defaults:

```bash
sdm init -dir sdm -dao internal/dbal -orm gorm -db pg
```

| option                    |                                                                                                               |
|---------------------------|---------------------------------------------------------------------------------------------------------------|
| `-dir <folder>`           | the folder of `sdm.xml` and `settings.xml`, relative to `go.mod`; its line in `.sdm`: `<folder>/go.dal`       |
| `-dao <folder>`           | the folder of the DAO, models go to `<folder>/models`; the last element is the Go package name                |
| `-orm no_orm\|sqlx\|gorm` | database/sql, sqlx or gorm: the data store; `field-assign-mode="0"` for `no_orm`, `"3"` for `sqlx` and `gorm` |
| `-db pg\|mysql\|sqlite`   | the database: type map and url in `settings.xml`, the data store for it                                       |

Options of the other commands:

| option          | default     |                                                                   |
|-----------------|-------------|-------------------------------------------------------------------|
| `-dir <folder>` | `go-sdm`    | the folder of `sdm.xml` and `settings.xml`                        |
| `-c N\|all`     | from `.sdm` | the configuration N of `.sdm`, or each of them, instead of `-dir` |

`SDM_PWD`, if set, overrides `pwd` of `settings.xml`.

### Several configurations: `.sdm`

A project may have more than one configuration, for example one per ORM. The IDE plug-ins keep
them in `.sdm`, a text file next to `go.mod`: their tool window shows its lines. `sdm` reads the
lines `<dir>/go.dal` and `<dir>/python.dal` of it, numbered from 1 in their order; `#` comments,
`---` separators and the other files are skipped, `|title` at the end is ignored:

```
--- sdm

no_orm/sdm/go.dal
sqlx/sdm/go.dal | sqlx
gorm/sdm/go.dal

---

README.md
```

Without `-dir` a command takes its configuration from there: `-c N` is the N-th, the only one
needs no `-c`. With several, `sdm` prints them with the ready command for each and, in the console,
asks for the number from the table or `all` (a wrong one is asked again, Enter cancels):

```
$ sdm gen -m
.sdm has 3 configurations:

  #     configuration         command
  1     no_orm/sdm/go.dal     sdm gen -m -c 1
  2     sqlx/sdm/go.dal       sdm gen -m -c 2
  3     gorm/sdm/go.dal       sdm gen -m -c 3
  all   (one after another)   sdm gen -m -c all

configuration 1..3 or all (Enter: cancel): 2
```

`-c all` runs the command for each configuration, one after another, each under its header
`--- N:<dir>/go.dal` and with its own progress; a failed one does not stop the rest, the exit code
is the worst of them. So one line in CI checks them all: `sdm val -c all`. `xml` takes one
configuration only.

Without a console (CI, a pipe) the table is all, exit 2: copy the command you need. No `go.dal` in
`.sdm` (or no `.sdm`) means `-dir go-sdm`, as before. `-dir` wins over `.sdm`; `-dir` together
with `-c` is an error. `go.dal` is the root file of the plug-in, `sdm` needs only its folder.
The language of a folder is its root file, as in the plug-in: `python.dal` there means Python,
`cpp.dal` C++, any other folder is Go.

### Try it in a dev container

[`.devcontainer`](.devcontainer) is Go with `sdm` installed and PostgreSQL 17 next to it, with the
tables `groups` and `tasks` and a function `tasks_by_priority` ([demo.sql](.devcontainer/demo.sql)).
Open the repository in VS Code (*Reopen in Container*) or in GitHub Codespaces, then in its terminal:

```bash
mkdir /tmp/demo && cd /tmp/demo && go mod init example.com/demo
sdm init -dir go-sdm -dao internal/dbal -orm no_orm -db pg
sdm xml -orm no_orm      # paste it into go-sdm/sdm.xml
```

## database/sql, sqlx or gorm

`sdm init` prepares the type map for all three. A class is generated for one of them by its
name in `sdm.xml`:

```xml

<dto-class name="Task" ref="tasks"/>       <!-- database/sql -->
<dto-class name="sqlx-Task" ref="tasks"/>  <!-- sqlx: db:"..." tags -->
<dto-class name="gorm-Task" ref="tasks"/>  <!-- gorm: gorm:"column:...;size:...;primaryKey;..." tags -->
```

## Data store

Two parts: the generated code (models and DAO) and the engine they run on, the data store in
their folder. The only thing you must not change in the engine is its adapter for the generated
DAO: `DS`, the `DataStore` interface and the `Set...` functions the DAO call. Everything else is
yours: the connection, logging, retries, whatever you need. `_ex` is the file for the connection;
keep it or not. Each database has its own data store, with only what it can do:

|                         | PostgreSQL           | MySQL               | SQLite           |
|-------------------------|----------------------|---------------------|------------------|
| driver                  | pgx                  | go-sql-driver/mysql | mattn/go-sqlite3 |
| generated keys          | `RETURNING`          | `LastInsertId`      | `LastInsertId`   |
| parameters              | `?` -> `$1, $2, ...` | `?`                 | `?`              |
| procedures: result sets | yes                  | yes                 | —                |
| ref-cursors, OUT, INOUT | yes                  | —                   | —                |

`sdm init -db ... -orm ...` writes the pair you choose. By hand, take it from
[`datastore/`](datastore), remove the first line `//go:build ignore` and set the package name of
your DAO folder:

|              | PostgreSQL                       | MySQL                                  | SQLite                                   |
|--------------|----------------------------------|----------------------------------------|------------------------------------------|
| database/sql | [pg/no_orm](datastore/pg/no_orm) | [mysql/no_orm](datastore/mysql/no_orm) | [sqlite/no_orm](datastore/sqlite/no_orm) |
| sqlx         | [pg/sqlx](datastore/pg/sqlx)     | [mysql/sqlx](datastore/mysql/sqlx)     | [sqlite/sqlx](datastore/sqlite/sqlx)     |
| gorm         | [pg/gorm](datastore/pg/gorm)     | [mysql/gorm](datastore/mysql/gorm)     | [sqlite/gorm](datastore/sqlite/gorm)     |

The connection is `DATABASE_URL` (or the default in `_ex`). All nine are made from the
templates in [`datastore/templates`](datastore/templates) by `go run ./cli/dsgen`; `go test`
fails if they differ.

`sdm gen` does not touch the data store. After `sdm` is updated, `sdm datastore` (`sdm ds`)
rewrites `data_store_<orm>.go` in the DAO folder of `settings.xml` with the one of this version: the
data store found there, for the database of `<db url>` (or `-db pg|mysql|sqlite`), with the package
of the file. `_ex` is never touched. `data_store_<orm>.go` is rewritten as a whole: if you changed it,
look at the diff and bring your changes back. Regenerate the DAO along with it (`sdm gen`): the
generated code and the adapter change together. It prints which one it took and why: the ORM by the file name, the
database
by `<db url>` (or `-db`):

```
$ sdm ds -c all
--- 1:gorm/sdm/go.dal
updated: gorm/dbal/data_store_gorm.go (gorm for mysql)

--- 2:sqlx/sdm/go.dal
up to date: sqlx/dbal/data_store_sqlx.go (sqlx for mysql)
```

A data store of the IDE plug-in (one file for all databases) becomes the one for your database
only, so the first `sdm ds` shows a large diff. `Out` and `InOut` are in every data store of
PostgreSQL and MySQL: the same DAO compile with no_orm, sqlx and gorm, even where MySQL cannot
fill OUT parameters.

## Type map

`<type detected="...">` in `settings.xml` is the type of a column as the driver names it:

| Database   | `detected`                                                                                              |
|------------|---------------------------------------------------------------------------------------------------------|
| PostgreSQL | `int4`, `int8`, `numeric`, `varchar`, `text`, `timestamptz`, `uuid`, `_text` (arrays), `refcursor`, ... |
| MySQL      | `INT`, `UNSIGNED BIGINT`, `DECIMAL`, `VARCHAR`, `TEXT`, `DATETIME`, `JSON`, ...                         |
| SQLite     | what the column is declared with: `INTEGER`, `VARCHAR`, `REAL`, ...                                     |

with a prefix for sqlx and gorm classes (`sqlx-int4`, `gorm-timestamptz`) and `+auto` for
the column of `auto="..."` (`gorm-uuid+auto`). `target` is the Go type of the field, its tags
and the function that reads it from a row:

```xml

<type detected="int4" target="int32${json} -> SetInt32"/>
```

`sdm init -db pg` writes the keys of PostgreSQL, `-db mysql` or `-db sqlite` those of MySQL or SQLite. To see which
names your database gives, empty the
type map (`<type-map default=""/>`) and generate: the code then has the raw names of the
driver instead of Go types. Where the driver says nothing about the type (MySQL parameters, SQLite expressions), the key
is `unknown`. A type written in `sdm.xml` (`<field type="int4">`,
`return-type="int8"`) goes through the same type map.

The `settings.xml` of the IDE plug-ins (Java names: `java.lang.Integer`, ...) works as is.
A Java name in `sdm.xml` (`<field type="java.lang.Integer">`) without a key in the type map
is replaced by the type of the column from the database, or by `unknown` if there is no column.

The XML files are meant to be edited in an IDE with XML Schema support:
GoLand out of the box, VS Code with the "XML" extension by Red Hat.

## Python

The same `sdm`, the same manifest and the same reverse engineering of the live database; the
output is Python without ORM: plain DB-API 2.0 (sqlite3, psycopg2/psycopg, mysql-connector-python)
behind a data store. It is what the Python target of the IDE plug-ins generates for no ORM, byte
for byte. Run `sdm` in the project folder, no `go.mod` is needed:

```bash
sdm init -lang python -dir sdm -dao dbal -db sqlite
```

`-dir`, `-dao` and `-db` are required, `-orm` is not for Python. `init` creates:

```
sdm/sdm.xml                classes to generate
sdm/settings.xml           folders, database URL, Python type map of the database
sdm/python.dal             the root file of the IDE plug-in: this folder is Python
sdm/*.xsd                  completion and validation in the IDE
dbal/data_store_no_orm.py  the data store for the database
```

and prints the line for `.sdm`: `sdm/python.dal`. The models and the DAO go to one package,
`<folders target>` of `settings.xml` (`dbal`; `app/dbal` is `from app.dbal.task import Task`).
The other commands are the same as for Go: `gen`, `val`, `ls`, `ds`, `-c N`; `sdm xml` needs no
`-orm` and names the FK access in snake_case.

The names follow the Python conventions: `snake_case` fields, parameters and methods, as in the
plug-in, whatever `field-names-mode` says. A DAO is a class over the data store:

```python
ds = create_ds(sqlite3.connect('app.sqlite3'))
dao = TasksDao(ds)
task = Task()
task.t_subject = 'subject'
dao.create_task(task)          # task.t_id is the generated value
tasks = dao.get_tasks_by_group(1)
ds.commit()
```

A class with a model (`sa-Task`, `dj-Task`) is an ORM class of the plug-in: `sdm` reports it as
an error of the class. `target` of the type map is the Python type in the docstrings of the
models and DAO (`int`, `str`, `Decimal`, `datetime`, ...), what the driver returns for the column.

The data store is the same deal as in Go: the generated part and the engine. Do not change the
adapter of the generated DAO in it, the methods of `DataStore` (`insert_row`, `exec_dml`,
`query_scalar`, `query_all_scalars`, `query_row`, `query_all_rows`) and `OutParam`; everything else
is yours, the connection included (`create_ds(conn)`). There is no `_ex` file: keep your part
where you like. Each database has its own data store, with only what it can do, made from
[`datastore/templates/data_store_no_orm.py.txt`](datastore/templates/data_store_no_orm.py.txt) by
`go run ./cli/dsgen`:

|                | PostgreSQL                          | MySQL                                  | SQLite                                   |
|----------------|-------------------------------------|----------------------------------------|------------------------------------------|
| file           | [python/pg](datastore/python/pg)    | [python/mysql](datastore/python/mysql) | [python/sqlite](datastore/python/sqlite) |
| generated keys | `RETURNING`                         | `lastrowid`                            | `lastrowid`                              |
| parameters     | `?` -> `%s`                         | `?` -> `%s`                            | `?`                                      |
| procedures     | `call`, OUT and INOUT by `OutParam` | `callproc`: result sets, OUT and INOUT | —                                        |

`sdm ds` rewrites `data_store_no_orm.py` as a whole: if you changed it, look at the diff and bring
your changes back.

## C++ (Qt)

The same again for C++ and Qt 5/6 (QtSql): what the C++ target of the IDE plug-ins generates, byte
for byte. Run `sdm` in the project folder:

```bash
sdm init -lang cpp -dir sdm -dao dal -db sqlite
```

`-dir`, `-dao` and `-db` are required, `-orm` is not for C++. `init` creates `sdm/sdm.xml`,
`sdm/settings.xml`, `sdm/cpp.dal` (the root file of the plug-in), the XSD and the data store
`dal/DataStore.h` and `dal/DataStore.cpp`, and prints the line for `.sdm`: `sdm/cpp.dal`. The models
and the DAO are headers `<Class>.h` in `<folders target>` (`dal`), next to the data store; `sdm xml`
needs no `-orm`. `<dto field-names-mode>` names the fields and the CRUD methods (the names of
`<query>` and `<exec-dml>` stay as written):

| `field-names-mode` | fields                    | CRUD methods                    |
|--------------------|---------------------------|---------------------------------|
| `0`                | as the columns: `task_id` | `createTask`, `readTaskList`    |
| `1`                | `taskID`                  | `createTask`, `readTaskList`    |
| `2`                | `task_id`                 | `create_task`, `read_task_list` |

An XML written for Go may have names a C++ compiler rejects; `gen` reports all of them for a DAO class
instead of writing it: a keyword as a method or a parameter (`register`, `delete`, `class`), and a
method named as the model class it returns (`OrdersByMonth` returning `CListReader<OrdersByMonth>`:
inside the DAO the method hides the class). Rename them in the XML. The same for a short Java type
of old XML, `get_city_by_country(String country_code)` or `return-type="Long"`, that the type map
leaves as is (no key, empty `default`): remove the type, and it comes from the metadata, or write the
C++ one (`CText`).

```cpp
CDataStore ds;
ds.open("app.sqlite3");
TasksDao dao(ds);
Task t;
t.t_subject.Value = "subject";
dao.createTask(t);                 // t.t_id is the generated value
CListReader2<Task> tasks;
dao.getTasksByGroup(t.g_id, tasks);
```

`target` of the type map is a value class of `DataStore.h`: `CInteger` (`qint64`), `CDouble`,
`CText` (`QString`), `CBlob` (`QByteArray`), and `CValue`, which holds anything in a `QVariant`
(`unknown`, JSON, arrays). `default` is for a type without a key; a type that is mapped already is
not mapped to `default` once more. A value class is a `Value` and two conversions, `toVariant()` for
a parameter and `fromVariant()` for a fetched column: a class of your own (`QDateTime`, `QUuid`, ...)
needs nothing else, the data store has no list of types to extend.

The data store: do not change its adapter, the value classes, `CRowProcessor`, `CListReader`,
`DL_STR`/`DL_T` and the methods `insert`, `execDML`, `queryRow`, `queryRowList` of `CDataStore`;
everything else is yours (`open`, transactions, your value classes). Each database has its own, from
[`datastore/templates/DataStore.h.txt`](datastore/templates/DataStore.h.txt) and
[`DataStore.cpp.txt`](datastore/templates/DataStore.cpp.txt) by `go run ./cli/dsgen`:

|                | PostgreSQL                    | MySQL                               | SQLite                                |
|----------------|-------------------------------|-------------------------------------|---------------------------------------|
| files          | [cpp/pg](datastore/cpp/pg)    | [cpp/mysql](datastore/cpp/mysql)    | [cpp/sqlite](datastore/cpp/sqlite)    |
| Qt driver      | `QPSQL`                       | `QMYSQL`                            | `QSQLITE`                             |
| generated keys | `select lastval()`            | `lastInsertId`                      | `lastInsertId`                        |
| `open`         | host, port, database, user, password | host, port, database, user, password | the file                        |

`sdm ds` rewrites both files as a whole.
